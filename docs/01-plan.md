# juece-grow · 规划方案

> 开源独立项目：管理你名下多个线上线下产品的获客、内容、线索与宣传，全部收在一个平台。
> 规划基线时间：2026-08。技术选型已按 2026 现状核实，避免一上线就落后。

## 1. 项目定位

一句话：一个自己的获客营销平台，替你把每个产品的官网、开方、留资入口、线索跟进统一管起来。

它不是一个给陌生人用的产品，而是你自己长期运营、治理自己全部推广资产的工具。

## 2. 要解决的问题

| 问题 | 现在的状态 | 平台要帮到的 |
|---|---|---|
| 每个产品官网各搭一套，样式、后台、域名零散 | 靠人记、靠人维护 | 一个平台统一管，站点模板化搭 |
| 文章发在零散平台，不被自己索引 | SEO 靠运气 | 站点可被搜索，文章结构化落地 |
| 抖音/小红书留言、私信、表单散落各处 | 容易漏、重复 | 统一收进线索池，打标去重分配 |
| 数据分散，说不清哪个渠道有效 | 凭感觉 | 线索来源可归因，渠道效果可看 |

## 3. 平台范围

### 包含（MVP 内）
- 多项目管理：一个工作区挂多个产品，每个产品独立站点。
- 内容管理：文章、页面区块在后台上编辑，站点渲染。
- 建站能力：可配置站点模板（首页/方案/文章/落地页），SEO 字段可填。
- 线索管理：访客表单线索，抖音/小红书手动入池，来源打标、去重合并、分配。
- 客服收件：接 Chatwoot，多渠道线索进统一收件箱。
- 权限与团队：账号、角色、站点成员归属。

### 不含（本期不做，留扩展）
- 不做电商交易、支付、订单。
- 不做批量营销自动化（邮件/短信群发后置）。
- 不做对外售卖的多租户计费——先做单平台自己用，代码开源可演进。

## 4. 核心模块

```
站点域: 站点/页面/区块/导航/SEO
内容域: 文章/富文本/媒体/多语言
线索域: 线索/表单/来源/去重/分配/跟进
收件域: Chatwoot 接入 / 统一收件箱
项目域: 项目/成员/角色/权限
运营域: 站点发布 / 统计 / 渠道归因
```

## 5. 技术选型（2026-08 基线）

见 docs/02-architecture.md，摘要：
- 公开站点：Astro（SSG 静态，内容/营销站/SEO 主场景）
- CMS/后台：Payload 3 自托管（MIT、角色不限），原生 admin/Auth/form/CRM，少自研
- 数据库：PostgreSQL 16（Payload 官方 stable 适配器），一套 schema 建模内容与线索，数据自持
- 富文本：Payload Lexical 内置
- 客服收件箱：Chatwoot，API 通道可接抖音/小红书
- UI 层：Tailwind + 现成组件，加快开发
- 选型原则：成熟框架优先，后台不自研，最快上线

## 6. 交付节奏（分阶段）

见 docs/06-roadmap.md：
- Phase 1 跑通链路：Astro + Payload + Postgres，单站点上线，文章可发可搜，表单线索入池
- Phase 2 多项目治理：多项目、成员角色、站点模板、来源归因
- Phase 3 全渠道收口：Chatwoot 收件箱，抖音小红书线索闭环，数据看板

## 7. 成功标准
1. 任一产品在该平台 10 分钟内搭出可被搜索的站点并发布。
2. 发文后能被搜索引擎收录（可提交站点地图）。
3. 网页/抖音/小红书线索都落进一个池子，可按来源归因。
4. 一个后台看全所有项目的站点与线索，不丢单、不重复。

## 8. 边界与红线
- CMS 后台用成熟框架 Payload（自托管）承担，不自研内容后台；数据不与外部 SaaS 绑定。
- 线索数据自持，Chatwoot 只是收件箱，线索主表在自有 Postgres。
- 升级以保证内容数据不丢失、配置不被覆盖优先；代码演进优先于视图美化。
- 命名遵循本项目规范（见 AGENTS.md），不与既有 juecesass 混用。
